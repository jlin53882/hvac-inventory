# 零用金月報維護文件

## 1. 範圍

零用金月報共用同一個 Report Shell，但一般零用金與工程零用金的明細模型、計算邏輯、editor 與 exporter 保持分離。

- 一般零用金：收入／支出／摘要／科目／上期餘額／本期餘額
- 工程零用金：Category → Group → Receipt → Detail，金額屬於 Receipt
- 共用：報表列表、篩選、權限、報表 header、狀態、分頁、Mobile card、操作入口與 loading/error/empty contract

不要將兩種明細塞進同一個 nullable entry model，也不要把 general calculator 與 engineering calculator 合併。

## 3. 共用 helper 維護規則

### 3.1 Modal Step Navigation

`pcSwitchModalStep(step, config)` 位於 `static/js/render/petty-cash.js`，由兩個 modal 呼叫：

- `pcModalGotoStep()`：一般零用金
- `engGotoStep()`：工程零用金

helper 只處理共通 UI state：

1. Step 1／Step 2 顯示切換
2. tab active class
3. footer 操作區顯示切換
4. 進入 Step 2 後呼叫 detail renderer

`validate` 與 `onDetail` 由各 modal 注入，禁止把 general／engineering business validation 寫進共用 helper。

### 3.2 Detail Header

`pcDetailHeaderHtml(report, engineering)` 統一輸出一般／工程 detail page 的：

- 期間與報表類型
- 報表歸屬人／製表人
- 檔名
- 返回、編輯、匯出、刪除操作

一般與工程的檔名格式、status badge 與 export label 仍由 helper 內的 type branch 控制；使用者資料必須維持 `esc()`。

### 3.3 Detail KPI

`pcDetailKpiCardHtml()` 與 `pcDetailKpiRowHtml()` 共用 KPI markup。呼叫端只提供 label、value、color 與 icon，禁止在 helper 內加入 general／engineering 計算邏輯。

### 3.4 Detail body 不共用

以下 renderer 保持分離：

- `pcGeneralEntryRowsHtml()`
- `pcGeneralMobileCardsHtml()`
- `engGroupHtml()`
- `engRenderDetail()` 的 category/group/receipt hierarchy

只有 presentation shell 可以共用；明細資料層級與計算不可合併。

### 3.5 PR8 responsive 決策（已確認）

以下是目前已確認、可作為 CSS canonical contract 的產品決策：

- 零用金 KPI 在 mobile 必須三張卡同一排；不要再使用「第一張滿列、其餘兩張並排」的舊 grid contract。
- KPI row 目前由 `style.petty-cash-pr8.css` 的 flex rule 負責，卡片使用等比例 flex 欄位；修改時必須保留三卡同排與文字可換行。
- 設定頁 `static/settings.html` 的零用金選單 `.pc-option-row` 採方案 A：左側顯示選單名稱／狀態，右側固定顯示編輯／刪除操作。
- `.pc-option-row` 不得恢復舊的 mobile `flex-direction: column` 方案 B；若要改版，必須先更新產品決策與 frontend contract test。
- 這兩項是設定頁／零用金 KPI 的 responsive contract，不涉及 API、資料模型或 Excel exporter。

### 3.6 Async freshness 與 financial write contract

零用金列表、KPI、detail 與 modal 都是非同步流程，維護時必須遵守：

- history／KPI request 必須使用 normalized filter snapshot、request sequence 與 current-filter guard；不能在 response 回來時重新讀 DOM 當作 request identity。
- detail／general modal／engineering modal 必須以 request/session token 綁定最新 report ID 與 modal type；stale response 不得寫入 `pcDetail`、`engData`、modal DOM 或 save target。
- general／engineering save 必須 single-flight；按鈕 loading／disabled 後，成功與失敗都必須在 `finally` 釋放狀態，失敗可安全 retry。
- petty cash create/update 在 duplicate check 與 write 前使用 `BEGIN IMMEDIATE`，保持 SELECT duplicate check、hierarchy/full replacement 與 commit 的 writer transaction atomicity。
- 修改上述流程時，至少執行 `tests/petty_cash_frontend_races.js` 與 general／engineering petty cash pytest；不可只做 source assertion。

## 6. Excel exporter 與工作表命名

一般與工程零用金共用 export entry point，但 exporter 與 template 分離：

- 一般零用金：`app/services/petty_cash_report.py` + `app/assets/零用金月報範本.xlsx`
- 工程零用金：`app/services/engineering_petty_cash.py` + `app/assets/工程零用金範本.xlsx`

工程 exporter 使用 template-copy-inject strategy：

1. 載入工程模板
2. 清除本次資料區值，不重畫模板 style
3. 依 Category → Group → Receipt → Detail 展開資料列
4. Receipt 金額只寫在第一個 detail row，並依 receipt detail rows merge
5. 重建 Category／Group／Receipt merge
6. 寫入 subtotal 與 grand total
7. 保留模板欄寬、字型、邊框與列高

### 工作表 tab 名稱

工作表名稱必須由報表期間動態產生，不能固定使用模板日期，也不能只取開始日期：

```text
單日：0904
同年度區間：0901-0904
跨年度：20261230-20270103
```

工程 exporter 使用 `engineering_sheet_title(start_date, end_date)` 實作此規則。

### 下載檔名與工作表名稱分離

- 下載檔名：期間 + filename note + 報表歸屬人 + 固定「工程零用金」
- 工作表名稱：只表達期間，不放 owner、note 或固定報表名稱

不要讓使用者直接輸入整串檔名，也不要把工作表名稱當成 Excel filename 使用。

### Excel 安全

每個使用者可控字串欄位都必須經過 `excel_safe()`，包含：

- 統編／統編標記
- 發票號碼／收據號碼
- Category
- Group
- Detail
- filename 相關文字

`V` 必須以文字原樣輸出，不可轉成圖片、boolean 或 `P`。

## 7. 後端邊界

- 一般零用金 route/service：`app/routes/petty_cash.py`、`app/services/petty_cash_report.py`
- 工程零用金 route/service：`app/routes/petty_cash.py`、`app/services/engineering_petty_cash.py`
- 共用 report shell／permission／list summary 可以共用，但 engineering amount 必須由 backend canonical calculation 提供
- 不可用 frontend total 作為唯一 truth source

## 8. 修改與收尾檢查

1. 先做 GitNexus impact，再修改 function。
2. 先跑受影響測試，確認 bug 版 contract 會失敗時才進行重構。
3. 新 helper 必須有呼叫點；取代舊邏輯時同一 commit 刪除舊版。
4. 既有 tracked 檔維持原本 EOL；新增 CSS 統一 LF。使用 `git -c core.whitespace=cr-at-eol diff --check`，不要因既有 CRLF 檔案造成假 diff。
5. 跑 security regression，確認新增 template interpolation 都有 `esc()`／`jsStr()` 或有理由的白名單。
6. commit 前跑 `gitnexus detect-changes --scope all`。
7. 修改 docs 或測試數量後，使用 `pytest --collect-only -q` 更新本文件與 `docs/單元測試維護文件.md`。

- **庫存警示語意（缺貨／低庫存）**：缺貨 = 非整組且 3 位小數正規化後數量 <= 0；低庫存 = 非整組且正規化後數量 > 0 且警示值 > 0 且數量 <= 警示值；兩者互斥。整組不計入一般缺貨／低庫存 KPI 與清單，整組可用性另由 shortage／insufficient 判定。`/api/stats` 的 `low_stock`／`zero_stock` 直接取同回應 `low_items`／`zero_items` 清單長度，KPI 與清單同源。

## 三、庫存資料完整性 invariant（2026-09-15 PR #13）

核心 invariant：**`total_qty >= prepared_qty >= 0`**。所有會減少庫存的操作都必須保護這個 invariant。

**核心 helper**：`app/services/inventory_stock.py` 的 `assert_projected_inventory(conn, item_id, stock_delta, prepared_delta=0)`——route 層在 `BEGIN IMMEDIATE` 後呼叫，驗證 projected state（projected_total >= projected_prepared >= 0）。

### Stock identity = item_stocks.id（不再是 location）

`PATCH /api/items/{id}` 的 stocks sync 使用 `item_stocks.id` 作為 identity：
- **Existing stock**：payload 帶 `id` + `stock_updated_at` → 用 id 匹配 DB row + 樂觀鎖 revision check（不一致 → 409）
- **New stock**：payload `id=null` → INSERT
- **Removed stock**：DB row 不在 payload → `qty≠0` 拒絕、`qty==0` 才 DELETE
- 前端 `edit.js` 的 `data-stock-id` + `data-stock-updated-at` 由 `renderEditStockRows` 寫入

### Location rename 兩階段（避免 UNIQUE 衝突）

當多筆 stock 同時 rename（swap A↔B 或 chain A→B→C），逐筆 UPDATE 會在中間狀態撞 `UNIQUE(item_id, location)`。修復：同一個 `BEGIN IMMEDIATE` transaction 內，Phase A 先搬到 transaction-unique temp location，Phase B 正式寫入 final location。

### BOM aggregation

`assemble_kit` 必須先按 `item_id` 聚合 BOM，再用 cumulative need 做 invariant check + deduction。`create_kit`/`update_kit` 拒絕 request 中重複 `item_id`。

### DELETE stock / item

- `DELETE /api/stocks/{sid}`：`qty≠0` 拒絕，`qty==0` 才允許 DELETE
- `DELETE /api/items/{id}`：同一 transaction 內清零 persisted stock + 寫 movement + soft-delete

### Stocktake

- 盤點用 **item total 級** prepared 判定（非 location 值）：`other_locations_total + actual >= prepared`
- 缺少 location 整批 409 拒絕（不 silent skip）

## 四、報價單作業（quotation）

- **建立／編輯**：報價單保存客戶資料、有效天數、稅別、備註與明細；明細會快照品項名稱/規格/單位/單價，並保留 `inventory_item_id` 來源關聯。
- **庫存帶入**：在報價單明細按「從庫存帶入」，搜尋單一庫存的品項、品牌或型號後直接加入明細。
- **歷史管理**：可依報價單號、客戶、聯絡資料或地址搜尋，支援編輯、刪除、Excel 與 PDF 匯出。
- **金額**：含稅報價以總額反推 5% 稅額；未稅報價以小計加計 5% 稅額。數量必須大於 0，單價不可為負數。
- **權限**：建立/編輯/刪除使用 `item-mgmt`；查詢與庫存帶入使用 `view`；Excel/PDF 匯出使用 `export`。

## 五、每日簽名日報表作業（signed-reports）

每日簽名日報表支援登入後查詢、預覽、下載、上傳與歷史管理。上傳者或具 `signed-report-delete-all` 權限者可編輯既有報表的 **日期、檔案、上傳人、備註**；未選擇新檔案時保留原檔，選擇新檔案時以新檔取代原檔並清理舊檔與媒體 metadata。編輯表單使用同一個 modal 與 `multipart/form-data`，不再使用多次 `prompt()`；替換檔案沿用 PDF/PNG/JPG/GIF/WebP 白名單與 20MB 上限。

- **安全**：檔案上限 20MB、副檔名白名單（PDF/PNG/JPG/GIF/WebP）、固定儲存檔名；替換檔案會重新驗證檔案內容與圖片解析度。
- **權限**：原始 `uploader_user_id` 仍是資料擁有者；修改「上傳人姓名」只改顯示欄位，不轉移檔案權限。
- **替換交易**：替換時先以 `BEGIN IMMEDIATE` 鎖定並提交 DB/asset 對映，再 finalize 新檔與清理舊檔；提交前失敗會回滾並刪新檔，提交後清理失敗只記錄 warning，不回滾已提交資料。
- **相容性**：不帶新檔時保留原始 file asset；沒有 file_assets 對映的 legacy 報表則回退使用 `stored_path` 清理。

### API

| Method | Path | 說明 |
|---|---|---|
| POST | `/api/signed-reports` | 上傳每日簽名日報表 |
| GET | `/api/signed-reports` | 歷史列表（日期/關鍵字/分頁） |
| GET | `/api/signed-reports/{id}/preview` | 登入後預覽 |

| DELETE | `/api/signed-reports/{id}` | 依權限刪除檔案與資料 |

## 七、出庫作業（stockout）

- **直接出庫**：單一庫存的卡片與表格模式皆顯示「🚚 已領出」完整文字按鈕 → 選數量/領出人 → 扣減庫存寫流水
- **待領出**：單一庫存的卡片與表格模式皆顯示「📤 待領出」完整文字按鈕 → 鎖定數量 → 之後可「領出」或「退回」
- **顯示一致性（2026-09-08）**：兩個出庫入口由 `buildInventoryStockoutActions()` 共用產生；手機卡片放在卡片底部，表格模式使用可辨識的文字按鈕（不只圖示），避免 RWD 分支漏掉功能。手機卡不可同時掛 desktop `.item-card`（其 `display:flex` 會把底部按鈕列擠往右側並被裁切）；狀態色改掛 `.m-card.warn`／`.m-card.danger`。入口權限必須直接看 `stockout`，不可用品項管理／庫存調整權限推導；僅有出庫權限者也必須看得到入口。
- **退回**：已領出/待領出皆可退回（數量加回）；已領出退回預設回原始 `source_stock_id`，可在 Modal 改選同品項的其他位置，庫存異動以 `return_stock_id` 實際回補位置為準。
- **來源位置與退回規則（2026-09-07）**：直接出庫與待領出確認均保存 `source_stock_id`、站點/位置 snapshot；退回流水保存 `return_stock_id` 與回補位置 snapshot。原始出庫位置已刪除或舊資料沒有來源時，不猜第一筆位置，必須由使用者選擇有效位置；跨多位置自動扣除的 legacy 紀錄也必須明確選擇。部分退回可再次退回，超退、跨品項 stock ID、退回位置不存在均回 400；編輯/刪除活動退回會同步調整實際庫存，已撤銷退回刪除流水但不重複扣庫存。
- **已退回操作（2026-09-09）**：正常、需修復、已撤銷的「退回已領出」流水，在已領出清單桌面表格與手機 ⋯ 選單都保留「刪除」入口；正常資料另保留編輯，舊資料另保留修復。刪除活動退回會扣回已補入庫存的數量並在原始出庫仍有退回時恢復可退狀態；已撤銷退回只刪除流水。
- **非庫存品項**：待領出/已領出頁可新增非庫存項目（不入庫存表）；**清單 site 過濾例外**——非庫存品項（is_deleted=1）不分 site 永遠顯示（`list_prepared`/`list_stock_outs` 的 site 條件含 `OR is_deleted = 1`；2026-08-16 修復：待領出原本 `AND site=?` 會擋掉非庫存，僅「全部」分片看得到）
- **非庫存 ⋯ 選單（2026-08-16 晚）**：待領出手機卡 ⋯ 選單對非庫存品項有效（`openPreparedSheet` 用 `preparedItems` fallback——`ALL_ITEMS` 不含 is_deleted=1 幽靈品項）；**非庫存無「退回」**（無庫存可回），選單/桌面按鈕只留「已領出 + 刪除」（手機 `if (!item.is_deleted)`、桌面 `${i.is_deleted ? '' : ...}`）
- **手機卡待領出 chip 佈局（2026-08-16 晚 V1b）**：「待領出」chip 移出品名行（名稱行只留品牌+名稱+非庫存 tag；型號/位置/chip/庫存全放品名下面）——`.m-card .nm` 是 nowrap+ellipsis，chip 塞名稱行會被長名截出誤導 ⋯（家豪實測回報）
- **待領出編輯 contract（2026-09-17）**：`PATCH /api/prepared/{id}` 一次保存 `prepared_qty`、`destination` 與允許的 metadata，並以 `updated_at` 做 optimistic lock；一般活動庫存 metadata 需要 `item-mgmt`，非庫存待領出沿用 stockout workflow。整組（`is_kit=1`）在待領出 modal 只可改數量／去向，`name/brand/code/unit` 必須回「整組庫存 → 編輯整組」，由 `PUT /api/kits/{kit_id}` 維持 `items`／`kits` 同步，prepared endpoint 不得複製 kit update 邏輯。分數輸入框使用 `type=text inputmode=decimal`，由 Qty parser 驗證 `1/4`、`3/4`、`1 1/2`；不可退回 generic item PATCH，避免非庫存資料 404。duplicate／optimistic-lock／invariant 失敗必須回語意化 400/409，不可變成 500。
- 併發防護：扣減採**守衛式原子 UPDATE**（`WHERE qty>=?`）——併發不超賣、不負庫存

## 八、盤點作業（stocktake）

- 盤點：選位置 → 輸入實際數量 → 提交 → 差異自動調整庫存 + 寫盤點紀錄
- **留空 = 確認**（2026-09-06）：實際數量留空表示與系統數量相同，提交時視為確認（diff=0）；填入與系統相同的數量也會送出（記錄盤點紀錄）
- 盤點輸入表分「🔧 整組」「📦 單一材料」兩個 tab（2026-08-13 Sarah 定案）：整組盤整組本身、單一材料盤一般品項
- 盤點表品項列顯示**圖片縮圖**（2026-08-16 家豪需求）：有照片顯示 `/uploads/{id}.jpg` 縮圖（點擊放大），無照片顯示 📷 佔位（`.cphoto` 樣式，與整組庫存頁表格同款）
- 整組 tab 展開**組成品項**（2026-08-16 家豪需求）：每個材料顯示縮圖+名稱+型號+「需 N ・ 系統 M 個」，且**每個組成品項也可輸入實際數量**（key=`itemId:location`，與單一材料盤點同一機制；後端 `POST /api/stocktake` 原本就支援材料 item_id+location，零後端改動）
- 歷史盤點：`/api/stocktake/dates` 列日期、可看每次差異明細
- **月底盤點提醒**（2026-09-06）：每月 25-31 日顯示提醒橫幅；**25-31日其中一天完成盤點後，當月不再顯示提醒**（localStorage 追蹤 `lastStocktakeMonth`，下個月 25 日再次顯示）

## 十一、效能與媒體儲存維護

### 庫存列表

- `GET /api/items` 未帶 `page` 時維持舊 list shape；新列表頁使用 `page`/`page_size`/`search`/`brands`/`categories`，回傳 `{items,total,page,page_size,stats}`。`stats` 依同一組 site/搜尋/品牌/分類條件計算完整 filtered item_count、total_qty、低庫存/缺貨數；只有按需的 `include_alert_items=1` request 才查詢 alert 摘要，不能從當頁 `items` 推導 Dashboard KPI。
- 篩選選項使用 `GET /api/items/facets?site=...`，避免為了建立品牌/分類選單下載全部品項。
- `IN (...)` 查詢使用保守分批；`brands + categories` 會先檢查 aggregate bind budget，過大的 filter/page 直接回 400，不把 SQLite bind/offset error 變成 500。
- 預設行事曆啟動不下載完整庫存；進入單一庫存才取目前頁，待領出/盤點/整組等需要完整資料的頁面才載入 full list。
- `GET /api/stats/summary` 一次回傳 all/office/warehouse，避免首頁對同一統計發出三次 request。
- 對應回歸測試集中在 `tests/test_media_storage.py`（分頁、unpaged metadata、filter budget、appointments chunk）與 `tests/test_file_asset_scripts.py`（導入/稽核腳本）。

### 行事曆與資料庫

- 月曆/搜尋列表使用批次 JOIN：行程主表、服務項目、建立/修改者、指派人員與 sync status 不得恢復逐筆 `_appt_row()` N+1。
- 新增查詢前先用 SQLite `EXPLAIN QUERY PLAN` 驗證；目前熱門查詢有 site/active、item/location、appointment date/start、assignee user/appt 複合索引。

### 既有檔案導入與健檢

```bash
# 先 dry-run，只列出待導入數量
.venv/Scripts/python.exe scripts/backfill_file_assets.py

# 確認範圍後才套用（可重跑，已存在 asset 會 skip）
.venv/Scripts/python.exe scripts/backfill_file_assets.py --apply

# 驗證 metadata、檔案存在、SHA-256 與孤兒檔
.venv/Scripts/python.exe scripts/audit_file_storage.py
```

- audit 必須回報 `ok: true`；`missing`、`checksum_mismatch`、`orphan_files` 任一非空都要先處理，不可直接刪檔。
- 正式文件（PDF/原始上傳檔）不做有損壓縮；ZIP 只作備份/封存/批次下載，不作線上單檔格式。
- HTML/JS/CSS 版本化 URL 使用長效 immutable cache；未版本化 static 維持短 cache；HTML no-cache；文字資源由 GZip middleware 壓縮。

## 十三、常見問題

| 症狀 | 原因 | 處理 |
|---|---|---|
| 數量調整被拒 | delta 使庫存 < 0（負庫存防護） | 先退回/盤點補正再調整 |

## 四個獨立庫存區（2026-09-15）

`items.site` 是庫存分片欄位，目前固定允許：

- `office`：辦公室
- `warehouse`：倉庫
- `van`：廂型車
- `truck`：貨車

四個 site 的品項主檔、位置庫存、統計、盤點、待領出／已領出、整組清單與異動查詢都必須依目前 site 隔離。相同物料可以在不同 site 建立不同主檔；不可用批次改位置 API 取代跨區調撥。

### 正式庫存調撥

`POST /api/inventory/transfers` 使用 transaction 同時完成：來源位置扣減、目標 site 主檔自動建立或重用、目標位置增加，以及來源／目標兩筆 movements。請求包含 `item_id`、`target_site`、`qty`，可指定 `source_location` 與 `target_location`；廂型車／貨車未指定目標位置時預設為「車內」。來源與目標不可相同，數量必須大於 0。

已組裝整組調撥時會在目標 site 複製整組定義與材料主檔；整組建立／編輯時，整組品項與所有材料必須屬於同一 site。整組若要換區，使用調撥，不要直接編輯 site。

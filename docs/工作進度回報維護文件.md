# 每日工作進度回報 維護文件

> 最後更新：2026-09-22
> 適用：Work Progress module（Gallery / photo management maintenance）
> 目的：快速定位 Work Progress 的資料、權限、前端狀態與 regression coverage。

## 1. 模組邊界

每日工作進度回報是獨立模組，不修改每日簽名日報表的資料表、API、媒體 category 或前端 namespace。

| 層 | 位置 | 契約 |
|---|---|---|
| API | `app/routes/work_progress.py` | `/api/work-progress`；登入、view、owner/global flags 由 backend enforcement 決定 |
| Snapshot sync | `app/services/work_progress.py`、`app/routes/appointments.py` | Appointment 編輯在同一 transaction 更新既有 calendar-owned snapshot |
| Storage | `app/services/file_storage.py` | `file_assets` + `work_progress/YYYY-MM/report_id/asset_id/`；原有 caller 不指定 custom path 時行為不變 |
| UI | `static/js/render/work-progress.js` | `wpr-*` namespace；history/detail/photo/gallery 使用 backend response |
| CSS | `static/css/style.work-progress.css` | Work Progress scoped selector；不要新增 global `.card`、`button` 等 selector |
| Permission UI | `static/js/perms.js` | `work-progress-view` 是 create/edit/delete 五個權限的前置 |

### 1.1 圖片載入與 Gallery 效能契約

- 列表/縮圖網格只使用 `thumbnail_url`；Gallery 只使用 `preview_url`；原圖僅由 `download_url` 下載。
- `wprOpenHistoryDetail()` 成功載入的最新 report 會供同一筆 detail 的 Gallery 重用，避免再次 GET 同一份 report；detail reload 會先失效舊快取，避免 mutation 後使用 stale photos。
- Gallery 顯示目前照片時，只背景預載前一張與後一張 preview，不會一次 eager load 全部照片；同一 URL 在本次 Gallery lifecycle 不建立重複的 preloader。
- Preloader 的 `Image` object 只在 request/decode inflight 階段由前端持有；成功後只保留已完成的 URL 狀態並釋放 Image reference，實際 bytes/resource 交由 browser cache 管理。失敗會釋放 inflight state 並允許 retry；Gallery close 會建立新的 lifecycle state，舊 Gallery 的 async callback 只能修改舊 state，不能污染新 Gallery。
- 初次開啟 Gallery 只預載 previous/next；使用者向前或向後移動時，額外預載該方向第二張 lookahead，最多維持三個相鄰 target，不會 eager load 全部照片。每次規劃 preload target 時會先 normalize wraparound index，排除 current image，並去除同一 render cycle 內重複的 target index。
- Work Progress detail thumbnails 使用 `loading="lazy"` 與 `decoding="async"`；Gallery current preview 不使用 lazy loading。
- 預載失敗只影響背景優化，主 `<img>` 仍直接設定 `src` 作為 fallback；切換圖片使用 `decoding="async"`。
- Work Progress 的 thumbnail、preview、download endpoint 都維持 report-scoped authorization，並回傳 `Cache-Control: private, max-age=86400`。不可改用未驗證 report ownership 的 generic `/media` route。

### 1.2 Gallery viewport contract

- 正式 Gallery dialog 使用固定 grid geometry：desktop `width: min(92vw, 1100px)`、`height: min(88vh, 760px)`；mobile 使用 `100vw × 100dvh`。
- `.wpr-gallery-stage` 是固定 dialog 內唯一 image stage，圖片使用 `max-width/max-height: 100%` 與 `object-fit: contain`；橫圖、直圖切換不得改變 header、caption 或 navigation 的位置。
- Gallery preload、rapid navigation、cache 與 lifecycle token 屬於獨立資料流；viewport CSS 不得改寫這些狀態。

### 1.3 Photo management and batch delete contract

- Normal mode thumbnail click 只開啟 Gallery；explicit management mode thumbnail click 只做 select/deselect，不開 Gallery。
- Selection state 以 `report_id + detail targetId` 為 key；selected/history 同一 report 的兩個 detail surface 不共享 selection。只有活著的 detail surface 持有管理 state：history list replace 前清理 `wpr-detail-*`，不影響 selected-detail；selected report switch、tab/page remount、report reload、成功刪除與完成管理都必須清理對應 state。State cleanup follows successful lifecycle transitions：navigation intent 或 destructive mutation 開始時不銷毀目前 detail state；舊 selected-detail 只在新 report 成功載入並取代，或 report deletion 成功後清理。
- Management toolbar 提供 selected count、全選目前 report photos、清除選取、完成與一次刪除選取。toggle/select-all/clear 都只做 local render，不重新 GET；刪除只發一個 `POST /api/work-progress/{report_id}/photos/batch-delete`，成功後才 fresh GET 並保留原 targetId。batch failure 保留 selection。
- Request body 是 `{"asset_ids": [...]}`，限制 1–20 個、asset ID 必須是 32 位 hex、重複 ID 直接拒絕。Backend 先驗證 report、權限、所有 asset 的 `category=work_progress`、`owner_type=work_progress_report`、`owner_id=report_id`，任一不符整批拒絕。
- DB row 與檔案刪除採 staging + transaction：檔案先移入 server-owned rollback staging，DB commit 成功才清除 staging；任一 staging/DB 失敗會 best-effort restore 全部檔案並 rollback rows。若 restore 部分失敗，後續檔案仍會繼續恢復，staging recovery material 保留供人工處理；正常 rollback 仍清除 staging。現況 domain 允許照片刪至 0 張，未新增至少一張的規則。

## 2. 權限契約

權限 keys：

- `work-progress-view`
- `work-progress-create`
- `work-progress-edit`
- `work-progress-edit-all`
- `work-progress-delete`
- `work-progress-delete-all`

### 2.1 Backend

`PUT /api/users/{user_id}/permissions` 會先合成此次 request 套用後的 effective state，再 normalize：

- `view = 0` 時，五個 dependent 一律寫成 `0`。
- dependent 任一由 `0` 開成 `1`，而 `view = 0` 時，自動將 `view` 開成 `1`。
- 不接受留下 `view = 0 + dependent = 1` 的資料庫狀態。
- `reset_all: true` 保留角色預設；目前四角色預設本身符合 dependency。

修改位置：`app/routes/users.py` 的 `_normalize_work_progress_permissions()` 與 `update_user_permissions()`。

### 2.2 Frontend permissions page

`static/js/perms.js` 的 `permToggle()` 會：

- 關閉 `work-progress-view`：同步取消五個 dependent checkbox。
- 開啟任一 dependent：同步開啟 `work-progress-view`。
- 每個自動變更都寫入 `permChanges`，並更新 `✏️ 自訂` source label。
- Save hint 使用 `Object.keys(permChanges).length`，顯示完整未儲存數量。

### 2.3 Work Progress page

`static/js/render/work-progress.js` 使用 `wprCanCreate()`：

- `view + create`：顯示完整建立表單。
- `view only`：保留頁面、KPI、history、detail、照片與下載；建立 card 顯示檢視權限提示，不渲染可操作表單。
- `wprSubmit()` 仍有 defensive guard，但這不是 backend security boundary。
- `can_edit` / `can_delete` 仍完全使用 backend response flags，不在前端重算 ownership。

### 2.4 Page Visibility integration (F16)

Work Progress follows PR #19's single access contract:

```text
canAccessPage('work-progress')
= page visibility contains work-progress
  AND permissions['work-progress-view']
```

- `work-progress` is registered in backend `PAGE_KEYS` and frontend `PAGE_VISIBILITY_TABS`.
- Admin Page Visibility UI labels it as `📸 每日工作進度回報` and can toggle it per user.
- All four role defaults include the page because all four roles have `work-progress-view`.
- Existing users are backfilled with only the missing `work-progress` row during `init_db()`; existing custom page rows are preserved by `INSERT OR IGNORE`.
- New users receive the row during user creation through the same visibility seed helper.
- Sidebar display and direct `work-progress` tab fallback both use `canAccessPage()`. No capability-only override may re-show the page after Page Visibility hides it.

## 3. Snapshot 與 attribution

- Calendar-owned：日期、時間、客戶、地址、指定服務、行事曆備註；Work Progress edit dialog 只能 readonly 顯示。
- Work-progress-owned：`uploader_name`、進度 note、施工照片。
- `uploader_user_id`、`created_by_username`、`created_by_display_name` 不可由 Work Progress PATCH 修改。
- `created_by_display_name` 是 users JOIN 的 live account display name。
- `uploader_name` 是 report 自己的 editable display snapshot。
- Appointment 改成無指定服務時，`service_name_snapshot` 必須清成空字串，不得保留舊服務。
- Appointment 刪除使用 `ON DELETE SET NULL`；report snapshot、照片、uploader attribution 仍保留。

## 7. 維護規則

1. 新增 Work Progress permission 時，同時更新 `app/database.py` seed、`tests/test_rbac_perms.py` 的 key/default assertions、`static/js/perms.js` dependency matrix；不要只加 UI row。
2. 改變 Calendar-owned snapshot 時，同時驗證 detail、history date range、KPI 與 appointment delete freeze；只測 detail 不足以證明跨月份一致性。
3. 照片 batch 必須驗證 DB row、asset variants、report folder 三者；partial failure 不可只看 HTTP status。
4. 前端 source assertion 必須切到函式或 handler block；避免只寫 `"work-progress-create" in js` 這類 false-positive。
5. `git diff --check` 對既有 CRLF 測試檔使用 `core.whitespace=cr-at-eol`；不可為消除誤報而把整個測試檔轉成 LF。
6. PR body 的測試數字、CI 狀態與 head SHA 必須在最後一輪工具驗證後更新；pending 不得寫成 pass。

# hvac-inventory 伺服器日誌維護文件

## 1. 日誌目標

所有 HTTP request 都要可以用同一組資訊追查：

- 時間
- HTTP method / path
- status code
- client IP
- duration（毫秒）
- request ID

未處理例外與 HTTP 5xx 另外寫入 error log；一般應用程式事件寫入 server log。Google Calendar 同步保留既有專用 log，同時透過 logging propagation 匯入 server log。

## 2. 日誌位置

伺服器啟動後自動建立當日目錄：

```text
logs/MMDD/server.log
logs/MMDD/access.log
logs/MMDD/error.log
logs/MMDD/gcal_sync.log
```

例如：

```text
logs/0908/server.log
logs/0908/access.log
logs/0908/error.log
logs/0908/gcal_sync.log
```

### 檔案用途

| 檔案 | 內容 |
|---|---|
| `server.log` | 全部 hvac 應用程式事件、啟動/停止、migration、auth、GCal 事件 |
| `access.log` | 每個 HTTP request 一行，包含 method/path/status/client/duration |
| `error.log` | ERROR 以上、未處理例外、HTTP 5xx |
| `gcal_sync.log` | 既有 Google Calendar 詳細同步紀錄；仍保留原查詢入口 |

## 3. 統一格式

```text
2026-09-08 23:10:00,123 [INFO] [hvac.access] [request_id=abc123...] GET /health status=200 client=127.0.0.1 duration_ms=1.2
```

`request_id` 會在 response header 回傳：

```text
X-Request-ID: abc123...
```

使用者回報錯誤時，優先要求提供發生時間與 `X-Request-ID`，再查 `access.log` 與 `error.log`。

## 4. 啟動方式

正式本機 server：

```bash
cd /c/Users/admin/workspace/hvac-inventory
env -u PYTHONPATH .venv/Scripts/python.exe -m uvicorn main:app --host 0.0.0.0 --port 8000
```

啟動後應看到：

```text
集中式 logging 已啟動 log_dir=...
server startup cwd=...
```

## 5. 快速查詢

Windows Git Bash：

```bash
# 查看今天所有 server 事件
tail -f logs/$(date +%m%d)/server.log

# 只看 request
grep 'hvac.access' logs/$(date +%m%d)/access.log

# 只看錯誤
grep -E '\[ERROR\]|Traceback|Unhandled request exception' logs/$(date +%m%d)/error.log

# 依 request ID 串起完整請求
grep -R 'abc123' logs/$(date +%m%d)/

# 找特定 endpoint
grep 'signed-reports' logs/$(date +%m%d)/access.log
```

PowerShell 使用者可改用 `Get-Content -Wait`、`Select-String`；本專案維護指令以 Git Bash 為準。

## 6. 已接入的入口

- `main.py` lifespan：啟動 logging、記錄 server startup/shutdown
- `app/middleware.py`：所有 HTTP request 統一記錄
- `app/database.py`：migration 訊息改走 logger
- `app/services/auth.py`：初始 admin 訊息改走 logger
- `app/services/sync_scheduler.py` / `gcal_sync.py`：既有 GCal logger 保留並匯入 server log

## 7. 安全與限制

- 不記錄 request body、Cookie、session token、密碼或上傳檔案內容。
- request log 使用 URL path，不直接記錄 query string，避免關鍵字或敏感參數進 log。
- logging 寫檔失敗不得阻斷 API；Python logging fallback 仍會輸出 console。
- `logs/` 是執行產物，不應 commit 進 Git。
- 目前已統一「request 層」與「未處理錯誤層」；各業務流程內的預期性錯誤仍應逐步補上有語意的 logger，不以大量重複 log 取代錯誤處理。

## 8. 維護檢查清單

- [ ] 啟動後 `server.log`、`access.log`、`error.log` 都存在
- [ ] `GET /health` response 有 `X-Request-ID`
- [ ] `access.log` 有 `GET /health status=200`
- [ ] 人為觸發 404/500 時，access/error log 可用 request ID 對上
- [ ] 每月檢查 `logs/` 是否需要壓縮或清理
- [ ] server 重啟後確認只有預期的 8000 listener

## 8000 啟動生命週期與 single-instance（2026-09-17）

### 問題根因

修正前本機 8000 曾同時存在手動 `start.bat`、`server_start.py --reload`、Windows `InventorySvc` 與外網 monitor 的啟動路徑；目前 `server_start.py` 已改為相容入口，會轉交 `scripts/start-server.ps1`，不再啟動 `--reload`。舊版 monitor 使用 detached `start` 開新視窗，沒有保存 PID，也沒有在啟動前確認既有 repo worker；Windows 關閉父程序後還可能留下 Python 子程序，形成孤兒 worker。多個 worker 讀到不同版本的 source，會造成「Network payload 正確，但 DB 被舊版 API 寫成空值」的資料流錯誤。

### 現行規則

- 唯一手動入口：`start.bat`，它只呼叫 `scripts\start-server.ps1`。
- `start-server.ps1` 使用 named mutex，避免並行啟動／重啟。
- `monitor.ps1` 也使用 named mutex；重複 monitor instance 會直接退出。
- 啟動前讀取 8000 listener；既有本專案 worker 會略過重複啟動。
- 非本專案程序佔用 8000 時直接停止並報錯，禁止強制終止未知服務。
- monitor 只呼叫 launcher 的 `-Restart`，不再自己 detached 開 `start.bat`。
- `-Restart` 只停止 command line／Python executable 可識別為本 repo 的 worker，並等待 port 釋放後再啟動。
- `InventorySvc` 是 Windows service 管理邊界；不得用 `taskkill /F /IM python.exe`，避免誤殺 Hermes 或其他 Python。

### 排查與恢復

```text
netstat -ano | findstr :8000
Get-NetTCPConnection -LocalPort 8000 -State Listen

# 手動正常啟動（已有本 repo worker 時會略過）
start.bat

# 明確重啟本 repo worker
powershell -NoProfile -ExecutionPolicy Bypass -File scripts\start-server.ps1 -Restart
```

若 launcher 回報「非 hvac-inventory process 佔用」，先用 PID 查明服務歸屬，不得直接殺程序。重啟後必驗證 `/health`、listener PID、process command line 與工作目錄，確認瀏覽器實際打到目前 workspace。

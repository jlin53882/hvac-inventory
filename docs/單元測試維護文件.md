## 三、測試架構與 fixture 模式（2026-08-14 優化後）

### 3.1 獨立 DB（每個測試隔離）
所有測試用 `tmp_path` + `monkeypatch.setattr("app.database.DB_PATH", str(test_db))`——每個測試獨立 SQLite，互不污染。

### 3.2 Session 注入（省 PBKDF2）
非登入測試的 admin fixture **不走 POST /api/auth/login**（每次 150ms PBKDF2 600k 迭代），改用：
```python
from app.services.auth import SESSION_COOKIE, create_session, init_admin_if_missing
init_admin_if_missing(_conn)
_token = create_session(_conn, admin_id)
c.cookies.set(SESSION_COOKIE, _token)
```
**登入/暴力破解測試保留真實登入**（test_users.py 的 rate-limit 等——它們就是要測登入）。

### 3.3 Module-scope 矩陣 fixture（test_rbac_perms）
80 個端點矩陣 case（viewer 403 + tech 白名單）是**唯讀檢查**，共用 module-scope fixture（`matrix_db`/`matrix_admin`/`matrix_viewer`/`matrix_tech`，整個 module 只建帳號登入一次）→ 129s → 29.5s。**狀態型測試**（覆蓋/保護規則/稽核）維持 function-scope 獨立 DB。

### 3.5 測試隔離教訓（2026-08-15）

**鐵則：任何測試不得在無 fixture 下使用 `TestClient`**——`with TestClient(app)` 會觸發 lifespan（`init_db` + `init_admin_if_missing`），若未 monkeypatch `DB_PATH` 就會打在正式 `inventory.db`。

真實案例：`test_users_requires_login` 原本無 fixture → 每次 pytest 連正式 DB（lifespan 建 schema/seed；若正式 DB users 表被清空會自動建 admin/admin123）。修法：加 `tmp_path, monkeypatch` + `monkeypatch.setattr("app.database.DB_PATH", str(tmp_path / "xxx.db"))`。

**防回歸測試**：`test_users_requires_login_does_not_touch_real_db` 斷言正式 DB 檔案 size/mtime 不變 + tmp DB 被初始化。

**commit 同步紀律**（v4 pro 審查 A1 教訓）：行為改動的測試必須**與 code 同 commit**——commit 與測試分離會讓 committed HEAD 無守護，CI/checkout 直接裸奔。

### 3.4 為何測試「慢」是故意的
登入驗證 PBKDF2-HMAC-SHA256 **600,000 次迭代 ≈150ms/次**——這是防暴力破解的安全設計，**絕不降低**（rate-limit 測試的慢是「該慢」）。加速靠 fixture 優化與並行，不靠弱化驗證。

## 四、新增功能的測試 SOP

### 4.1 新增 API 端點
1. 端點掛 `require_perm(key)`（一般 RBAC）；需撤權立即生效的敏感資源使用 `require_db_perm(key)`（dependency 執行時直接從 DB 重算）
2. **加入 `test_rbac_perms.py` 的 WRITE_ENDPOINTS 矩陣**（viewer→403 自動覆蓋）——新端點第一件事就是進矩陣
3. 寫該端點的功能測試（對應測試檔）
4. 跑 `./scripts/run-tests.sh frontend`（security 守衛）+ 相關組

### 4.2 新增前端（JS/HTML）
1. **使用者可控資料內插一律 `esc()` / `jsStr()`**（utils.js）
2. 跑 `./scripts/run-tests.sh frontend`——若掃描器列你的內插為「未審核」：安全（數字主鍵/常數三元）→ 加 `REVIEWED_SAFE_BODIES` 白名單**含註解**；否則補 esc()
3. 行為改動同步補 `test_frontend_assets.py` 斷言

### 4.3 修改既有功能
1. 找出對應測試檔 → 先跑該組（確認紅/綠基線）
2. 改完跑該組 + 受影響組（如改後端 API 回應形狀 → frontend 組也要跑，它斷前後端契約）
3. commit 前跑 `all`（並行 ~44s 很快，不用省）

### 4.4 待領出／整組／server lifecycle 變更
1. 修改 prepared API 或 modal：至少跑 `test_prepared_api.py`、`test_frontend_assets.py`、`test_quantity.py`；涉及權限時再跑 `rbac`。
2. 修改 kit metadata：確認待領出 endpoint **拒絕整組 metadata**，只由 `PUT /api/kits/{id}` 維護 kit domain；測試不可只做 source string assertion，必須驗證 response 與 DB invariant。
3. 修改 launcher／monitor：跑 `test_server_lifecycle.py`，並在 Windows 實機驗證 listener 數量、listener PID、`/health`；mutex 只包 startup critical section，不能包 server lifetime。


4. 最終測試數以 `python -m pytest --collect-only -q` 實測後才回寫文件；目前 live baseline 為 1738。

### 4.5 Excel 匯出 correctness regression

修改 `app/routes/export.py` 時，`tests/test_export.py` 必須同步覆蓋：

- snapshot 包含 active kit；位置明細與庫存總表仍維持一 item／一 location 語意。
- 異動紀錄保留 soft-deleted item 與 `site=''` non-stock 的歷史流水；snapshot 仍排除 deleted item。
- movement reason 使用 production contract 分類：領出準備、出庫、退回已領出、盤點、調撥、組裝／拆解與刪除清零。
- custom range 使用左閉右開 `[start, end)`，inclusive calendar days 上限為 366。
- 同一 business transaction 若寫入多筆 movements，transaction entry point 只取得一次 `movement_time.now_sql()`，所有相關 rows 共用同一 `created_at`；transfer 跨午夜回歸固定 23:59:59 → 00:00:00 不得拆月。

目前新 production movement writer 統一使用 Asia/Taipei business time 的 naive `YYYY-MM-DD HH:MM:SS`；user-entered movement datetime 也會先做真實日曆驗證與格式 normalize。SQLite `CURRENT_TIMESTAMP` 只保留為既有 schema 的 legacy fallback，不再由 production writer 依賴；既有 ambiguous historical rows 不在本輪猜測或整表回寫。匯出使用同一 formatter，並以 exact boundary regression 固定 `[start, end)` 行為。

### 4.6 Excel 報表相容性與公式回歸

Excel 匯出需以 `load_workbook(..., data_only=False)` 檢查六張 Sheet、`tblInventory`／`tblPosition`／`tblMovement`、A1 公式、number format、隱藏警示 helper 與 Dynamic Array blacklist；derived values 不得改回 Python 固定數字。

### 4.5 批次/Queue/Scheduler 的 No-op 設計

所有批次處理函式都要先定義空輸入契約，再取得任何外部資源：

```python
if not items:
    return empty_result
```

空工作應滿足「零 I/O」不變量：不連 DB、不建立網路 client、不讀取專用 schema、不取得檔案鎖；測試需 monkeypatch 對應資源並在被呼叫時直接失敗，避免完整 fixture 把不必要的依賴掩蓋掉。回傳型別也必須與實際結果一致，包含空輸入的結果形狀。

實例：`sync_pending([])` 必須回傳 `(0, 0, {})`，且不得呼叫 `get_db()`；相關防回歸位於 `tests/test_gcal_sync.py`。

## 3. Google 行事曆同步（完整說明）

### 3.1 架構

```
使用者(多人)               hvac FastAPI Server
──改行事曆──▶ appointments write (POST/PUT/DELETE) commit成功
                   │
                   ▼
       mark_sync_pending(appt_id, op[, map_rows])
                   │   [依指派人綁定的 gcal_key 解析目標 key 集合]
                   ▼
       appointment_sync_queue (appointment_id, key_id) 複合主鍵
                   ▲  每 N 分鐘掃描；編輯防抖 5 分鐘
       sync_scheduler (background threading；startup 無 key 仍建立 worker)
                   │
                   ▼
       gcal_sync: 對每個目標 key 各用該 key 的 Service Account
                   insert/patch/delete 到對應 calendar
                   + appointment_gcal_map (appointment_id, key_id)
                   │
                   ▼
       Google Calendar API (多行事曆)
```

### 3.2 方案 C：Service Account 管理

**家豪統建所有 Service Account，廠商只需做一件事——把 email 加入行事曆分享。**

- 同步方向：**單向**（本地 → Google，Google 端改動不回寫）
- Multi-Key：每把 key 對應一個廠商的 SA，同一行程可同步到多本行事曆
- **GCal 同步錯誤通知（2026-09-13）**：同步失敗通知必須顯示 `Key「名稱」／Calendar「ID」`，不能只顯示 Calendar ID 或數字 key_id；每把 Key 的錯誤要分列並保留錯誤類型與次數。404 通常需優先檢查該 Key 的 Calendar ID、Service Account 分享權限與 Calendar 是否仍存在。
- **Per-Key Popup 提醒（2026-09-13）**：每把 Key 獨立保存 1~5 筆 Popup reminders，Google API payload 使用 `useDefault=false`；Email reminder 不再接受、不顯示、不同步。提醒時間由 UI 的週／天／小時／分鐘轉為 minutes 保存，重新載入時再逆向顯示。`parse_popup_reminders()` 是 API response 與同步引擎共用的唯一解析入口。
- **Reminders UI 顯示限制（2026-09-17 實測確認）**：Google Calendar API 正確存入 per-event reminders（`useDefault=false` + overrides），API `events().get()` 讀回的 `reminders` 欄位100% 正確。但 Google Calendar 網頁版 UI 會顯示行事曆預設提醒（通常30 分鐘），忽略事件 overrides。**根因**：Service Account 建立的事件，reminders 綁定在 Creator（服務帳號）的私有視圖；個人帳號登入網頁版時，UI 讀不到服務帳號的 private reminders，退回顯示使用者個人行事曆預設值。**這是 Google Calendar API 的設計限制，不是系統 bug。** 實際通知仍會在正確時間發送（後端資料正確）。`scripts/test_gcal_reminders.py` 為完整測試腳本（測試後已刪除）。

- 使用者綁 key：行程依指派人綁定的 key 決定同步到哪本行事曆

### 3.4 同步機制

**mark_sync_pending**（`appointments.py`）：
- 行程 create/update/delete 成功後呼叫
- 依 `resolve_target_keys()` 解析目標 key 集合
- 每個目標 key 寫一列 `appointment_sync_queue`

**resolve_target_keys**（`gcal_sync.py`）：
- 查指派人員的 `users.gcal_key` → 找對應的 `gcal_keys.id`
- fallback：指派人沒綁 key 時，同步到**所有啟用 key**；使用者換綁定 Key 時，既有行程會建立新 target 並對舊 target 建 D queue。
- fallback 只納入 `is_active=1 AND COALESCE(pending_calendar_id,'')=''` 的 key（2026-09-17 修復：排除 migration pending key，避免 fallback 數量虛增）。
- **B2 已修（2026-08-28）**：fallback 保持同步全部 key，但 orphan 判斷改看「有綁定者」的 key 集合（不看沒綁 key 的 fallback 情境）。全沒綁 key 時不刪 orphan（guard 命中）。

**sync_scheduler**（background threading）：
- application startup 一律建立 scheduler worker；啟動時沒有 active key 只會單輪 no-op，第一把 key 後不需重啟即可 backfill；worker dead 時 `start()` 依 `is_alive()` 重建。
- 每 N 分鐘掃描 `appointment_sync_queue`；normal run 遵守 5 分鐘編輯防抖，force run 略過防抖但仍排除 attempts >= 5。queue 寫入後會喚醒 worker。
- scheduler/force/sync caller 共用 lock，避免同一 appointment + key 同時 insert/patch；sync 與 Key 刪除先共用跨 process key-level lock，再以 per-event lock 保護 remote cleanup 與 local cascade；Google network 不在 SQLite write transaction 內。
- 失敗重試：最多 5 次；1~4 次為 retrying，>=5 保留 exhausted queue row、google_event_id 與安全錯誤分類 `last_error`，需管理者指定列 Retry。credential path 不寫入 queue，API 也會遮罩歷史 raw error。
- `/api/gcal-sync-status` 提供 thread/last run/last success/active key 與 queue health；另回傳 `paused_count` 讓停用 Key 的 queue 不被誤解為可立即執行。
- `/api/gcal-sync-queue` 提供含 deleted appointment、Key active 狀態的管理清單。

**卡片同步狀態（2026-09-17）**：
- 同步引擎仍是 Multi-Key；卡片顯示改以目前登入者的 `users.gcal_key` 為視角，不再讓其他 Key 的失敗／等待污染個人狀態。
- API 回傳 `my_sync_status`；一般使用者只看到自己的狀態與錯誤。非指派人員顯示 `未指派給你`，未綁 Key 或停用 Key 不計入團隊有效比例。
- 具有 `gcal-sync-team-view` 權限的使用者可取得 `team_sync`：分子／分母以指派人員計算，共用同一 Key 的多人仍各算一人；未綁定、停用、停用帳號另列，不計入 `eligible_people`；`partial_failed` / `partial_retrying` 分別歸入 failed/retrying。Admin 預設擁有此唯讀權限。
- 無 `gcal-sync-team-view` 時，`team_sync` 為 `null`，不得取得其他 assignee 的狀態、錯誤、Key 或 fallback metadata。
- **Fallback 文字（2026-09-17）**：未指派行程的同步標籤顯示「未指派，同步至所有帳號（X 個）」，不再使用「fallback」字樣，避免使用者誤認為錯誤狀態。對應 `calTeamSyncLabel()` 與 `calShowTeamSyncDetails()` 兩處。
- `gcal-sync-force` 獨立控制 team member Retry / Retry All；Team View 不會自動授予重試能力。
- retry-all 重用 `resolve_target_keys()` 的 fallback target，再排除 pending calendar migration；retry-user 只接受有效指派人員的 active Key，避免 retry scope 與 queue creation 分歧。
- Migration pending 時保留原本 failed/partial status 與 `migration_pending=true`，但 personal/team detail 的 `can_retry=false`；普通 Card Retry 不得介入 D cleanup lifecycle。
- `/api/gcal-sync-queue/reset-mine` 只依 session 重試本人 queue；Admin 透過 `/api/gcal-sync-queue/reset-scope` 可重試指定指派人員或該行程全部有效同步目標。卡片的「全體」不等同全系統 queue，已同步／未命中 queue 的人不顯示無效 Retry action。

**F9–F11 lifecycle contract（PR #15，2026-09-17）**：
- `resolve_target_keys()` 是未來 C/U 的 effective target resolver：只納入 active user、active key，且排除 `pending_calendar_id` migration key。
- `resolve_assigned_key_ids()` 是目前 appointment relationship resolver：只要 appointment 仍保留該 assignee 與其 `gcal_key`，即使 user inactive、key paused 或 migration pending，仍保留在 assigned relationship 中。
- orphan D cleanup 使用 `resolve_assigned_key_ids()`，不可改用 effective target 集合；inactive user 單純停用不得刪除既有 map／Google event。
- appointment 有 assignee 時，移除 assignee 才會使其 Key 成為 orphan；appointment 完全沒有 assignee 時，沿用 active-key fallback，不能把空的 assigned set 視為全部 orphan。
- appointment update 可保留既有 inactive assignee，但不得新增 inactive assignee；因此 mixed active/inactive appointment 修改時只對 active effective targets 做 C/U，歷史 inactive map 保留。
- user deactivate 只停止未來 C/U／一般 retry，不自動建立 D；user re-enable 只 reconcile 目前 active assignment 的 missing/stale queue，migration pending Key 仍跳過。
- user re-enable 同時換 Key 時走單一 transition orchestration：新 Key 補 assignment，舊 Key 僅在不再被任何目前關係使用時做 D cleanup，避免兩套 reconcile 重複處理。

**sync_pending**（`gcal_sync.py`）：
- 速率限制：per-key 每分鐘 min(480, 8000/活躍key數) 次
- 冪等：C op 前先查 map（insert 成功但 map 寫入失敗時重試不重複）
- data_hash 由 `build_event()` 最終 Google Event payload 經 canonical JSON（`ensure_ascii=False`、`sort_keys=True`、固定 separators）後 SHA-256 產生；service name、assignee display name、effective duration/location/transparency/reminders 都自然納入。hash 相同只收斂 queue，不呼叫 PATCH/INSERT。C insert 會先 checkpoint remote id，map 寫入失敗重試時改走 patch。
- C insert 使用 appointment+key 的 deterministic eventId；跨 process 同時建立時 Google 只允許一個成功，另一個 409 會 patch 同一 ID，避免 duplicate Event。
- 成功後只在 queue 仍為相同 `last_modified_at` + `op_type` 時寫回 `appointment_gcal_map` 並刪 queue；新版本 completion 不會覆蓋 map/吞掉 queue。C/U remote 成功後若本地 appointment 已消失，建立 compensating D queue。
- 網路呼叫在交易外，不持 SQLite 寫鎖。
- `gcal_keys.reminders`、global transparency/use_location/default duration、service name、assignee display name 變更會 invalidation 受影響既有 mappings；hash 相同時仍 skip API。
- **410 冪等處理**：D op 收到 Google `HttpError 410 Resource has been deleted` 時視為遠端已完成刪除，清除 map/queue，不計入失敗。
- **過期 queue 保底清理**：C/U op 找不到本地 appointment 且尚未有 remote side effect 時才清除 queue；D op 即使本地 appointment 已刪除，仍使用保留的 google_event_id 呼叫 DELETE，403/429/timeout/network/credential failure 要保留並增加 attempts。
- **A3 已修（2026-08-28）**：D op 成功後同步刪 `appointment_gcal_map`，防止換回時 patch 404。
- **A4 已修（2026-08-28）**：`mark_sync_pending` 的 hash-skip 已移除，C/U op 每次都進 queue（queue 為暫態，不值得為省 row 引入 op_type 錯位風險）。
- **A2 冪等保護**：C op 先查 map，且 insert 成功後先 checkpoint remote id 到 queue；map 寫入失敗時重試改走 patch，不重複 insert。

**Key 刪除行為**：
- 刪 key 前先取得該 key 的跨 process key-level lock，再從 `appointment_gcal_map` 撈出所有 `google_event_id`，逐筆呼叫 Google API `events().delete()`；每個 appointment + key 的 remote cleanup 與後續 local cascade 另在同一 per-event lock 內，避免 unmapped C queue 在 snapshot 後建立 orphan。
- 全部成功（含 Google 410 已不存在）才刪 key，DB `ON DELETE CASCADE` 再清 `appointment_gcal_map` + `appointment_sync_queue`；行程本體不受影響。
- 任一遠端刪除失敗時回 409，保留 key/map，並建立或更新該 event 的 D queue（含 attempts/安全錯誤分類）；管理者可在同步問題清單逐列 Retry，避免 cascade 造成 Google orphan。

### 3.5 Calendar migration reliability（PR #12，2026-09-16）

Calendar Key 變更使用既有 `calendar_id` + `pending_calendar_id` migration state，不新增 migration table/framework。

- migration pending 期間：old `calendar_id` 保持為遠端 D cleanup 使用的 Calendar；C/U 不執行，D 可以執行。
- migration 開始時，沒有 remote ID 的 stale C/U queue 可清除；已有 `google_event_id` 的 C/U 必須轉成 D，保留 `appointment_id`、`key_id`、remote ID；既有 D 不刪除。
- scheduler 每輪先執行 `recover_pending_calendar_migrations()`；只將 pending mapping 中仍有 remote ID 的資料補成 D，且保留 attempts / last_error，recovery 必須 idempotent。
- recovery 後對所有 `pending_calendar_id IS NOT NULL` 的 Key 呼叫既有 `maybe_finalize_calendar_migration(key_id)`。若 `appointment_gcal_map = 0` 且 D queue = 0，即使 Key inactive 也可 finalize。
- finalize 的 Calendar switch 與 new Calendar backfill queue 建立使用同一個 DB transaction；backfill 任一步失敗必須 rollback，不能留下 Calendar 已切換但 queue=0 的半完成狀態。
- active Key finalize 後依最新 appointment / assignment 建立 C/U；inactive Key 只完成切換，不建立 C/U，重新啟用時才 backfill。
- scheduler finalize 在呼叫 `maybe_finalize_calendar_migration()` 前取得既有 `gcal_sync._key_process_lock(key_id)`；pending Key list scan 保持在 lock 外，取得 lock 後由 finalize 重新讀最新 DB state，避免 PUT mutation 與 finalize 交錯使用 stale target。

故障排查時先檢查：

1. `gcal_keys.calendar_id` / `pending_calendar_id` 是否仍為合法 migration state。
2. `appointment_gcal_map` 是否仍有 map。
3. `appointment_sync_queue` 是否有 D、attempts、last_error 或 exhausted 狀態。
4. 是否應等待既有 scheduler recovery / finalize，而不是手動刪 map、切 Calendar 或重建 migration state。

## 7. 故障排除

| 症狀 | 可能原因 | 解法 |
|------|----------|------|
| 同步後 Google 行事曆沒出現事件 | SA email 未加入行事曆分享 | 請廠商把 email 加入分享 |
| 同步後 Google 行事曆沒出現事件 | calendar_id 錯誤 | 到行事曆設定頁確認 ID |
| 同步失敗 403 | 廠商移除了分享 | 請廠商重新加回 email |
| 同步失敗 404 | calendar_id 格式錯誤 | 確認格式為 `xxx@group.calendar.google.com` |
| 同步失敗 410 | Google 事件已先被刪除 | 系統會自動視為刪除完成並清理對映；不需重新分享 |
| 同步失敗 `KeyError: N` | 本地行程已刪除但舊 C/U queue 殘留 | 系統會自動清理過期 queue；若是舊版本殘留，查看同步佇列確認已消失 |
| 新增 key 失敗 | name 重複 | 換一個名稱 |
| JSON 檔找不到 | 路徑錯誤 | 確認相對路徑從專案根目錄算 |
| 事件結束時間等於開始時間 | 前端只填開始時間 | 系統自動加 1 小時（build_event 兜底） |
| 同步一直失敗不消失 | attempts ≥ 5 | 查 `appointment_sync_queue` 的 `last_error`，修正後手動刪該列重觸發 |
| 行程卡片顯示 ❌ | 同步失敗 | 點卡片查看錯誤，常見 403（廠商移除分享）或 404（calendar_id 錯） |
| 同步 log 看不到 | logs/ 目錄不存在 | server 重啟會自動建 |

# 行事曆同步系統問題分析（2026-09-15）

## 背景

hvac-inventory 行事曆同步系統（Google Calendar 單向同步）於 2026-08-27 上線，運行至今發現若干設計時未注意到的問題。本文整理 Tier A/B/C 分類與建議修復方案。

---

## Tier A — 應該修（影響功能正確性）

### A1. 失敗 D（刪除）任務永久卡住

**症狀**：行事曆刪除後，scheduler 發送 D 到 Google → 如果失敗 5 次 → 永遠卡在 `appointment_sync_queue`，Google 端殘留孤兒事件。

**根因**：`classify_sync_exception` 只處理 `AppointmentNotFoundForSync`（本地來源已刪除）和 `410`（遠端已刪除），但不處理「D 失敗且本地已刪除」的情境。

**影響**：Google 日曆上殘留已取消的行程，使用者看到「部分同步失敗」但無法清除。

**建議修復**：在 `_run_once` 的 D 任務失敗路徑中，檢查本地行程是否存在。若已不存在 → 清 queue + map，標記為 resolved。

---

### A2. Scheduler 崩潰無自動重啟

**症狀**：`_thread` 是 daemon thread，如果意外掛掉（未預期例外、OOM 等），不會自動重啟。

**根因**：`_loop` 有 `try/except` 捕捉例外，但如果有 `SystemExit` 或 thread 層級異常，thread 會靜默終止。

**影響**：同步完全停止，沒有通知，直到下次 server 重啟。

**建議修復**：
1. `_loop` 外層加 `while not _stop.is_set()` 重啟機制
2. 或新增 `/api/gcal-sync-status` endpoint 讓前端/監控檢查 scheduler 狀態
3. scheduler 掛掉時發 Discord 通知

---

### A3. `_backfill_all_appointments` 沒有去重

**症狀**：新增/啟用 key 時，把所有行程加入 sync_queue，包括已同步過的。

**根因**：`INSERT ... ON CONFLICT DO UPDATE` 會覆蓋，不會報錯，但多做無用同步。

**影響**：大量 API 呼叫浪費（100 個行程 × 3 個 key = 300 次呼叫，其中大部分是已同步的）。

**建議修復**：backfill SQL 加 `AND NOT EXISTS (SELECT 1 FROM appointment_gcal_map WHERE appointment_id=a.id AND key_id=?)`。

---

## Tier B — 可改善（影響效率或可維護性）

### B1. 舊的 gcal_map 列無限期累積

**症狀**：key 停用/刪除後，map 列仍留在 DB。

**根因**：key 刪除時 DB CASCADE 只清 `appointment_gcal_map` 中「該 key 的列」，但 key 停用不會清。

**影響**：398 列 map，其中包含 inactive key=1 的歷史列。不影響功能，但佔空間。

**建議**：key 停用時不清 map（保留歷史同步紀錄）；key 刪除時 DB CASCADE 自動清。

---

### B2. Discord 通知只有 scheduler 觸發時才發

**症狀**：scheduler 崩潰時，完全沒有通知。

**根因**：通知只在 `_run_once` 完成後發送，scheduler 掛掉不會觸發。

**建議**：加 health check 機制（定期 ping scheduler thread，掛掉時發通知）。

---

### B3. Debounce 窗口 5 分鐘可能不夠

**症狀**：5 分鐘內連續編輯同一行程，最後一次的變更才會被同步。

**根因**：`_due_ids` 用 `last_modified_at` 距今 ≥5 分鐘判定 due，中間的變更會被合併。

**影響**：使用者可能不知道中間的變更沒被即時同步。

**建議**：可考慮縮短到 2-3 分鐘，或在前端顯示「同步中…」狀態。

---

## Tier C — 目前 OK 但可注意

### C1. 多人同時編輯同一行程

樂觀鎖（`last_modified_at` 版本條件）防止 scheduler 覆蓋。但兩個使用者同時編輯，後存的會覆蓋先存的（標準行為）。

### C2. DB 直接修改不會觸發同步

如果有人直接改 `appointments` 表，不會自動加入 sync_queue。需透過 API 操作。

### C3. 速率限制

per-user 480/min、專案級 8000/min（80% 安全邊際）。大量同步時可能觸發等待。

## 建議優先順序

1. **A1**（D 任務清理）— 避免 Google 端殘留孤兒事件
2. **A3**（backfill 去重）— 減少不必要的 API 呼叫
3. **A2**（scheduler 健康檢查）— 避免同步靜默停止
4. **B2**（scheduler 掉線通知）— 與 A2 配套

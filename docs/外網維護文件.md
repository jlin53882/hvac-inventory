# 外網連線 維護文件（Tailscale Funnel 固定網址 + 健康監控）

> 最後更新：2026-08-13
> 適用：hvac-inventory 系統 🌐 外網連線與自動復原
> 目的：讓維護者（人類或 AI agent）清楚知道「外網怎麼開、網址為什麼固定、掛了怎麼自動恢復、換機要注意什麼」

## 1. 架構總覽

```
手機/同事瀏覽器（不需安裝任何軟體）
        │  https://node.tail13203e.ts.net（固定網址）
        ▼
Tailscale Funnel relay 伺服器（Tailscale 官方，全球節點）
        │  Tailscale 加密通道（本機真實 IP 不外露）
        ▼
本機 Tailscale 服務（tailscaled，Windows 服務常駐）
        │  http://127.0.0.1:8000
        ▼
庫存系統 server（uvicorn main:app，由 start.bat 啟動）
```

| 角色 | 說明 |
|---|---|
| **主方案** | Tailscale Funnel → 固定網址 `https://node.tail13203e.ts.net` |
| **備援方案** | cloudflared quick tunnel → 網址每次啟動會變（`外網啟動-cloudflared.bat`） |
| **外網使用者** | 不需安裝 Tailscale / 任何軟體，瀏覽器直接開網址 |

## 2. 固定網址機制（為什麼是 node.tail13203e.ts.net）

```
https://node.tail13203e.ts.net
        │          │
    機器名稱     tailnet 名稱（綁定帳號 jlin53882@gmail.com）
```

| 部分 | 說明 | 換新電腦後 |
|---|---|---|
| `tail13203e.ts.net` | tailnet 後綴，綁定 Tailscale 帳號 | ✅ 不變（同帳號登入同 tailnet） |
| `node` | 機器名稱（這台電腦在 Tailscale 的名字） | ❌ 會變（新電腦 hostname 不同） |

> ⚠️ 本機 hostname 是中文「客廳電腦-家豪」，Tailscale 自動以 ASCII `node` 作為 DNS 名稱。
> **換新電腦** → 網址前綴會變 → 全員需重新登入（cookie 綁 domain）。
> 若要換機後維持同一網址：新電腦執行 `tailscale set --hostname node`（同 tailnet 不能同時兩台同名，舊機需先登出/關閉）。

## 3. 啟動方式

### 主方案：Tailscale Funnel（固定網址）
```bat
雙擊 外網啟動.bat
```
→ 呼叫 `scripts/tailscale-funnel-notify.ps1`：
1. 確認 Tailscale 已連線（`tailscale ip`）
2. 確認 Funnel 已開通（`tailscale funnel status`）；未開 → `tailscale funnel --bg 8000`
3. **連通性檢查**（HTTP 2xx/3xx）通過才推播固定網址到 Discord webhook
4. 顯示固定網址

### 備援方案：cloudflared（網址每次變動）
```bat
雙擊 外網啟動-cloudflared.bat
```
→ 呼叫 `scripts/tunnel-notify.ps1`（原 quick tunnel 流程，網址每次重啟會變，全員需重登）

### 關閉外網
- Funnel 模式：執行 `tailscale funnel --https=443 off`，或停止 Tailscale 服務
- 關閉「外網啟動」視窗**不會**關閉外網（Funnel 是 Tailscale 服務層常駐）

## 4. 健康監控（自動復原）

### 監控循環（scripts/monitor.ps1，背景常駐）

每 **10 分鐘**檢查兩項，同一問題**連續 2 次**才推 Discord 通知（防抖防洗版）：

| 檢查對象 | 掛掉時動作 | 通知內容 |
|---|---|---|
| 本機 `http://127.0.0.1:8000/health` | 透過 single-instance launcher 重啟 server；恢復後發送恢復通知 | 故障：「本機 server 無回應，已自動重啟」；恢復：「本機 server 已恢復」 |
| Funnel 公網 `https://node.tail13203e.ts.net/health` | 透過 Cloudflare DNS 解析公網 A 記錄，繞過本機 MagicDNS；失效時觸發 `HVAC-Tailscale-Recovery` 高權限工作排程重啟 Tailscale 服務；恢復後發送恢復通知 | 故障：「Funnel 公網無回應，已重啟 Tailscale」；恢復：「Funnel 公網已恢復」 |

- Funnel 健康檢查**不可只用本機網域解析**：本機 Tailscale 會將 `node.tail13203e.ts.net` 解析成 `100.x` 內部 IP，會漏判「本機正常、外網 TLS 直接斷線」的控制平面同步故障。
- `HVAC-Tailscale-Recovery` 以 `SYSTEM / HIGHEST` 執行 `scripts/restart-tailscale-service.ps1`，避免背景 monitor 遇到 UAC 卡住。

- 每輪寫入 heartbeat 檔（`%TEMP%\hvac_monitor_heartbeat.txt`）
- 計數狀態存 `%TEMP%\hvac_monitor_state.json`

### 監控的監控（scripts/watchdog-check.ps1 + 工作排程器）

| 項目 | 說明 |
|---|---|
| 排程名稱 | `HVAC-Monitor`（開機後以 SYSTEM/HIGHEST 執行）、`HVAC-Monitor-Watchdog`（Windows 工作排程器每 10 分鐘） |
| 頻率 | monitor 常駐；watchdog 每 10 分鐘 |
| 檢查 | ① monitor.ps1 是否在跑 ② heartbeat 是否過舊（>15 分鐘 = 卡死） |
| 動作 | monitor 掛掉/卡死 → 透過 `HVAC-Monitor` 工作排程重啟；Discord 通知 |

### 安裝 / 移除
```bat
:: 安裝（需系統管理員）：註冊 watchdog + Tailscale 高權限復原任務 + 啟動監控
scripts\install-monitor.bat

:: 手動移除排程
schtasks /delete /tn "HVAC-Monitor" /f
schtasks /delete /tn "HVAC-Monitor-Watchdog" /f
schtasks /delete /tn "HVAC-Tailscale-Recovery" /f
```

### 手動測試監控
```powershell
# 單輪檢查（正常狀態）
powershell -File scripts\monitor.ps1 -Once

# 單輪 + DryRun（只顯示動作不實際執行）
powershell -File scripts\monitor.ps1 -Once -DryRun

# 模擬本機掛掉
powershell -File scripts\monitor.ps1 -Once -DryRun -LocalUrl "http://127.0.0.1:9999/health"

# 檢查 watchdog 是否正常
powershell -File scripts\watchdog-check.ps1
```

## 6. 故障排除

| 症狀 | 原因 | 處理 |
|---|---|---|
| 網址打不開（HTTP 000/exit 35） | Tailscale 官方服務中斷（憑證/DNS 建立失敗） | 查 https://status.tailscale.com；等恢復後重跑 `外網啟動.bat` 或 monitor 自動重建 |
| `tailscale cert` 回報 500 failed to create DNS record | Tailscale 官方問題（2026-08-12 發生過） | 同上，非本機設定錯誤 |
| Funnel 顯示開通但外部連不上 | 公開 DNS 記錄尚未生效 | 等待數分鐘後重試 |
| 監控沒在跑 | 被關閉或卡死 | 工作排程器 10 分鐘內自動拉起；或手動 `powershell -File scripts\monitor.ps1` |
| 換新電腦後網址變了 | 機器名稱不同 | `tailscale set --hostname node`（舊機先登出） |
| 需要完全機器無關的固定網址 | 機器名綁定限制 | 自購網域 + Cloudflare named tunnel（$3-12/年） |

## 8000 啟動生命週期與 single-instance（2026-09-17）

### 問題根因

修正前本機 8000 曾同時存在手動 `start.bat`、`server_start.py --reload`、Windows `InventorySvc` 與外網 monitor 的啟動路徑；目前 `server_start.py` 已改為相容入口，會轉交 `scripts/start-server.ps1`，不再啟動 `--reload`。舊版 monitor 使用 detached `start` 開新視窗，沒有保存 PID，也沒有在啟動前確認既有 repo worker；Windows 關閉父程序後還可能留下 Python 子程序，形成孤兒 worker。多個 worker 讀到不同版本的 source，會造成「Network payload 正確，但 DB 被舊版 API 寫成空值」的資料流錯誤。

### 現行規則

- 唯一手動入口：`start.bat`，它只呼叫 `scripts\start-server.ps1`。
- `start-server.ps1` 使用 named mutex，避免並行啟動／重啟。
- `monitor.ps1` 也使用 named mutex；重複 monitor instance 會直接退出。
- 啟動前讀取 8000 listener；既有本專案 worker 會略過重複啟動。
- 非本專案程序佔用 8000 時直接停止並報錯，禁止強制終止未知服務。
- monitor 只呼叫 launcher 的 `-Restart`，不再自己 detached 開 `start.bat`。
- `-Restart` 只停止 command line／Python executable 可識別為本 repo 的 worker，並等待 port 釋放後再啟動。
- launcher 使用 `Start-Process -PassThru`，只等待 port ready 後釋放 mutex；後續 `Wait-Process` 發生在 mutex 外，因此 hung worker 仍可被下一次 `-Restart` 接管。
- `InventorySvc` 是 Windows service 管理邊界；不得用 `taskkill /F /IM python.exe`，避免誤殺 Hermes 或其他 Python。

### 排查與恢復

```text
netstat -ano | findstr :8000
Get-NetTCPConnection -LocalPort 8000 -State Listen

# 手動正常啟動（已有本 repo worker 時會略過）
start.bat

# 明確重啟本 repo worker
powershell -NoProfile -ExecutionPolicy Bypass -File scripts\start-server.ps1 -Restart
```

若 launcher 回報「非 hvac-inventory process 佔用」，先用 PID 查明服務歸屬，不得直接殺程序。重啟後必驗證 `/health`、listener PID、process command line 與工作目錄，確認瀏覽器實際打到目前 workspace。

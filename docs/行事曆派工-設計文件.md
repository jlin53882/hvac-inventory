## 二、選項資料管理（本文件核心：不寫死）

### 2.1 原則

> **凡是「未來可能增減、但選項數量有限」的資料，一律存在資料庫字典表，前端選單由 API 動態載入。程式碼不得寫死任何業務選項。**

### 2.2 現況盤點（哪些寫死、哪些已資料驅動）

| 選項 | 現況 | 來源 | 判定 |
|---|---|---|---|
| 服務類別（維修/保養/安裝） | demo 寫死在 `<select>` | `calendar_demo.html` | ❌ 要改 |
| 負責人員（老闆/老闆娘/雙人） | demo 寫死 `boss`/`lady` 字串 | `calendar_demo.html` | ❌ 要改 |
| 品項單位（個/罐/瓶/包…) | 寫死在新增/編輯 modal 的 `<select>` | `static/index.html` | ❌ 建議順帶改（見 §2.6） |
| 庫存位置補全 | 從 `item_stocks` 自動彙整 | `GET /api/locations`（lookup.py） | ✅ 已是資料驅動先例 |
| 客戶/案場 | 已領出為自由輸入 + datalist | `movements.destination` | ✅ 沿用此模式 |

### 2.3 服務類別 → `service_types` 字典表

```sql
CREATE TABLE IF NOT EXISTS service_types (
    id          INTEGER PRIMARY KEY AUTOINCREMENT,
    name        TEXT NOT NULL UNIQUE,        -- 例：「維修」「保養」「安裝」
    sort_order  INTEGER NOT NULL DEFAULT 0,  -- 下拉排序（數字小在前）
    is_active   INTEGER NOT NULL DEFAULT 1   -- 停用=新增時不出現在下拉；舊行程仍正常顯示
);
```

- 種子資料：`維修`、`保養`、`安裝`（與 demo 一致，但寫在 DB 不是程式碼）
- 前端下拉：開啟行事曆頁時 `GET /api/service-types` 動態填入，**JS 內零硬編碼**
- 停用（is_active=0）而非刪除：歷史行程的類別名稱不能失效
- 新增類別（例如「報價勘查」）→ 資料庫加一列就好，**不需要改程式、不需要重啟**

### 2.4 負責人員 → 直接綁 `users` 表（不另建人員字典）

系統已有帳號體系（`users`：username / display_name / role）。負責人員就是**可派工的帳號**：

- 指派對象 = `is_active=1 AND role != 'viewer'` 的所有使用者（admin/user 都可被指派）
- 下拉資料來源：`GET /api/assignable-users` → 回 `[{id, display_name, username}]`
- **雙人出勤** = 一筆行程指派多個使用者 → 用關聯表（見 §3），不再用 demo 的魔法字串 `'both'`

**好處**：
- 未來加師傅/加人手 → 建帳號即可出現在派工下拉，零程式改動
- 改名 → 改 `display_name`，所有歷史行事曆自動同步顯示新名
- 停用帳號 → 不再可被指派，但舊行程仍保留名字樣貌

### 2.4.1 負責人員名單來源：方案甲（綁 users）vs 方案乙（獨立 assignees 表）⚠️ 待決策

家豪提案（message.txt）建議獨立 `assignees` 表（id, name, role, color_code, is_active）。與「直接綁 users 表」對比：

| 方案 | 資料來源 | 優點 | 缺點 |
|---|---|---|---|
| **甲：綁 users 表**（本文建議） | `users`（is_active=1 且 role≠viewer） | 單一名單不重複；權限自動整合；viewer 角色剛好給「只看出工行程」的師傅；改名/停用統一管理 | 完全不登入系統的人員無法被指派 |
| **乙：獨立 assignees 表**（提案） | `assignees(id, name, role, color_code, is_active)` | 可指派不登入系統的人（如不碰手機的師傅） | 兩套名單（users+assignees）要想清楚誰維護；新員工要建兩次；權限對應要多一層 |

> 建議 **方案甲**：目前僅老闆/老闆娘兩人；未來師傅若能看行程（哪怕只讀），用 viewer 帳號即涵蓋。提案中的 `color_code` 概念保留 → 採方案甲時放進 `users` 表新增欄位（§9 決策 3）。僅當日後出現「必須排班但絕不登入」的人員，再評估獨立表。
> 另註：採用多對多 `appointment_assignees`（§3）後，**不需要「雙人」這種組合型選項**（demo 的 `'both'`），雙人 = 一筆行程指派兩人，字典更乾淨。

### 2.5 客戶/案場 → 自由輸入 + datalist 自動彙整

比照既有 `/api/locations` 先例（從資料庫 DISTINCT 彙整，不維護字典）：
- 新 API `GET /api/appointment-clients`：從 `appointments.client_name` 彙整過去輸入過的客戶/案場
- 與已領出的 `dest-list`（movements.destination）**合併成同一份補全清單** → 派工填的客戶、領料填的客戶，兩邊互相補全、漸趨一致，未來才能做「案場 × 用料」關聯分析
- 仍允許自由輸入（資料驅動補全 ≠ 強制選單）

### 2.6 （建議順帶）品項單位 `units` 字典表

現有新增/編輯 modal 的單位下拉寫死 10 種（個/罐/瓶/包/組/米/條/捲/盤/套）。同屬「會想擴充」的選項，建議同模式改成 `units` 字典表 + `GET /api/units`。**可獨立成小任務，不綁行事曆**，家豪決定是否一起做。

### 2.7 字典管理界面（誰能改）

| 角色 | 服務類別 / 單位管理 | 人員指派來源 |
|---|---|---|
| 👑 admin | ✅ 可新增/改名/停用/排序 | 使用者管理頁（既有） |
| 👤 user | ❌ 只能選用 | 只能選用 |
| 👀 viewer | ❌ 只能看（連下拉都是唯讀顯示） | 只能看 |

- **第一階段**：字典只有「種子資料 + 管理 API + 前端動態載入」，管理 UI（類別增刪停用的 modal）與使用者管理頁同款模式
- **第二階段**（可選）：把「服務類別管理」塞進既有使用者管理 modal 一個分頁，或獨立「⚙️ 設定」頁
- 因為種子是 SQL，最快可先用 DB 直接改 → 但**正式建議第一階段就把簡易管理 modal 做出來**（很便宜：沿用 users.js modal 模式，一個表格 + 新增列 + 停用開關）

### 2.8 重構路線圖（對照家豪提案三階段）

| 階段 | 做法 | 適用時機 | 本系統結論 |
|---|---|---|---|
| 短期 | 集中 `config.js`（SYSTEM_CONFIG）+ 動態渲染 | 純前端／離線 demo，無後端 | ⏭️ **跳過**：系統已是 FastAPI+SQLite，直接做終點 |
| 中長期（終點） | DB 字典表 + 管理 API + 前端動態載入 | 正式系統 | ✅ **採用**（本文件 §2.3 / §2.4 主軸） |
| 顯示層 | `getAssigneeLabel()` 等 Mapping helper 集中翻譯，render 層零硬編碼 | 任何時候 | ✅ **採用**（正式 `calendar.js` 一律查表，不寫 `assignee==='boss'?'老闆':...`） |

> 為何跳過 config.js：它的好處是「不動後端」——但本系統後端就是自家的，DB 種子 + 一個 GET API 的成本 ≈ 前端多一層 config 的成本，且避免「config.js 寫一次、DB 又要寫一次」的雙重維護。config.js 僅保留給 `sketches/calendar-ui-prototype.html` 這類離線 demo 使用。
> 提案中的 `SYSTEM_CONFIG` 動態渲染、衝突檢查改查表等寫法 ✅ 保留為前端實作慣例（§2.3 的 API 就是它未來的 fetch 來源）。

## 三、資料模型

```sql
CREATE TABLE IF NOT EXISTS appointments (
    id              INTEGER PRIMARY KEY AUTOINCREMENT,
    client_name     TEXT NOT NULL,               -- 客戶姓名與戶號 / 案場
    address         TEXT DEFAULT '',             -- 地址（選填，家豪 2026-08-12 新增；匯出日報表時進備註區「地址：」）
    service_type_id INTEGER REFERENCES service_types(id),
    date            TEXT NOT NULL,               -- YYYY-MM-DD
    start_time      TEXT NOT NULL,               -- HH:MM（24 小時制字串排序即時間序）
    end_time        TEXT NOT NULL,
    note            TEXT DEFAULT '',
    created_by      INTEGER REFERENCES users(id),
    created_at      TIMESTAMP DEFAULT CURRENT_TIMESTAMP,
    updated_at      TIMESTAMP DEFAULT CURRENT_TIMESTAMP
);

CREATE TABLE IF NOT EXISTS appointment_assignees (
    id             INTEGER PRIMARY KEY AUTOINCREMENT,
    appointment_id INTEGER NOT NULL REFERENCES appointments(id) ON DELETE CASCADE,
    user_id        INTEGER NOT NULL REFERENCES users(id),
    UNIQUE(appointment_id, user_id)              -- 同一行程不會重複指派同一人
);

-- 字典表（§2.3）
CREATE TABLE IF NOT EXISTS service_types (
    id          INTEGER PRIMARY KEY AUTOINCREMENT,
    name        TEXT NOT NULL UNIQUE,
    sort_order  INTEGER NOT NULL DEFAULT 0,
    is_active   INTEGER NOT NULL DEFAULT 1
);
```

**設計要點：**
- `date`/`start_time`/`end_time` 用 TEXT（ISO 格式）— 與系統既有 `stocktakes.take_date`、`movements.created_at` 慣例一致
- demo 用 `Date.now()` 當 id → 改由 SQLite AUTOINCREMENT
- demo 用 `toISOString()` 取日期 → **UTC 時區 bug**（台灣晚上會跳一天），正式版一律本地日期字串
- demo 用 `innerHTML` 塞客戶/備註 → **XSS**，正式版用 `textContent` 渲染（呼應安全性報告 A2）

## 五、防衝突規則（前端提示 + 後端強制）

衝突 = **同一人、同一天、時間區間重疊**。前端送出前先擋（即時提示），後端 POST/PUT 再驗證（防同時多裝置/直打 API）。

後端查詢（編輯時帶 `exclude_id` 排除自己）：

```sql
SELECT a.id, a.client_name, a.start_time, a.end_time, u.display_name
FROM appointments a
JOIN appointment_assignees aa ON aa.appointment_id = a.id
JOIN users u ON u.id = aa.user_id
WHERE a.date = ? AND aa.user_id = ?
  AND a.start_time < ? AND a.end_time > ?   -- 重疊條件
  AND a.id != ?
```

- 重疊定義與 demo 相同：`新開始 < 舊結束 且 新結束 > 舊開始`（相鄰 09:00–11:00／11:00–13:00 不算衝突）
- 雙人行程 = 同時查兩名指派者
- 命中 → 回 `409 Conflict` + 衝突明細（誰、幾點、哪筆）；前端顯示紅色警示條，不寫入
- 基本驗證：`end > start`（同 demo）

## 十、匯出工程日報表（mmdd）——範本填值法（2026-08-12 定案）

> **家豪指示**：匯出要用他提供的 `0811.xlsx`（紙本工程日誌掃描版）當**範本**直接填值，不要自己重刻版面——格式問題交給範本，以後要改格式只改範本檔、不用改程式。

### 10.1 架構（正式版）

```
使用者的 0811.xlsx（範本，進版控）
   ↓ openpyxl.load_workbook（保留全部樣式/合併格）
   ↓ 填值：工程師 A2、日期 D2、行程填入 5 個預留區塊
   ↓ ws.title = mmdd（0812）+ save 工程日報表0812.xlsx
```

- **範本檔位置**：`app/assets/工程日誌範本.xlsx`（進版控；sketches/ 內為開發複本）
- **Sheet 名**：改為 mmdd（範本原為「1204」）
- **好處**：版面（框線/合併格/欄寬/字型）零重刻；改格式 = 改範本檔

### 10.2 範本結構（已完整解析）

- A1:K1 標題「振佳空調 工程日誌」／ A2 工程師／ D2 日期（合併 D2:K2）
- **5 個預留區塊**，每塊 7 列：
  - 資料列（區塊1=row4、區塊2=row11、區塊3=row18、區塊4=row25、區塊5=row32）：
    A=項次、B=時間、C=地點、D/F/H/J=保養/維修/安裝/配管 勾選欄（區塊3 的 J 欄印「查看」為範本印刷差異，保留不動）

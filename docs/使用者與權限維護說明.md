## 一、角色總覽

| 角色 | 代號 | 說明 |
|---|---|---|
| 🛡️ **管理員** | `admin` | 系統全部權限（含使用者管理與權限設定），負責帳號與系統維護；**系統至少須保留 1 位啟用管理員** |
| 👤 **使用者** | `user` | 依矩陣取得完整庫存與部分行事曆／報表能力；**無法管理帳號**。實際可用入口還受 Page Visibility 與個人覆蓋控制 |
| 🔧 **工程師** | `tech` | 依矩陣取得行事曆、簽名報表與部分操作能力；不能管理帳號。實際能力以 permission matrix 與個人覆蓋為準 |
| 👀 **檢視者** | `viewer` | 預設以檢視為主，但目前具 `change-own-password` 與 `quotation-upload-manage` owner capability；其他寫入仍依矩陣、個人覆蓋與 endpoint scope 判定 |

**權限模型（2026-08-13 起）**：角色 = 預設模板；**個人開關**可在權限頁覆蓋（例：開放某檢視者的品項編輯權限）。覆蓋立即生效、不需重新登入；Page Visibility 只控制入口顯示，不取代 RBAC capability 或後端 authorization。

**新增帳號時的角色下拉**（單筆與批次）均提供這四種選項（admin / user / tech / viewer）。

**`item-mgmt` contract**：`item-mgmt` 同時控制庫存品項 CRUD、一般報價單 CRUD，以及新增／編輯品項等 modal 內的單位快速新增；它是正常品項工作流的共享 mutation capability。單位停用、排序與收編仍由 `unit-mgmt` 控制。`signed-report-upload` 控制上傳 capability；`signed-report-edit` 與 `signed-report-delete` 分別控制 owner edit/delete capability；`signed-report-delete-all` 是 global management scope。

**Quotation Upload contract**：`quotation-upload-manage` 控制 owner edit/delete capability；`quotation-upload-manage-all` 是 cross-owner global scope；兩者必須同時滿足 capability AND scope。上傳目前仍由登入保護，不由這兩顆 permission 控制。

**Petty Cash contract**：`petty-cash-view/create/edit/delete/config` 依各自 capability 控制；`petty-cash-delete-all` 目前是 temporary compatibility global scope，不可解讀成單獨的 delete capability。上述權限在 UI 分類為「報表與零用金」，分類只供權限頁篩選，不參與授權判定。

**Google Calendar contract**：`gcal-sync-manage`、`gcal-sync-force`、`gcal-sync-team-view` 與 `gcal-keys-manage` 各自控制同步設定、強制同步、團隊狀態與 Service Account Key 管理；不可只以 `unit-mgmt` 代替。

**Page Visibility contract**：`page-visibility-manage` 只管理每位使用者的 Page Visibility 設定，不等同於一般 Page Access capability；實際入口仍是 Page Visibility ∩ RBAC Capability。

**註**：登入／登出為所有登入者皆可使用，不列入矩陣。

### 2.1 強制規則（不可被個人覆蓋）

| 規則 | 說明 |
|---|---|
| `view` 不可關閉 | 瀏覽為基底權限，所有角色一律可看（統計/匯出等可個別關閉） |
| `user-mgmt` 僅管理員 | 非 admin 角色看不到此開關（權限頁自動鎖定）；admin 恆為開啟 |
| `change-own-password` 四角色預設開啟 | Admin、User、Tech、Viewer 均具 capability；Page Visibility 可控制修改密碼入口是否顯示，個人 permission override 仍可調整實際能力 |
| `svc-type-mgmt`／`unit-mgmt` 非 admin 不可開 | 服務項目管理僅限管理員 |
| 不能修改自己的權限 | 任何帳號不能改自己的權限、不能停用／刪除自己（權限頁對自己鎖定） |
| 唯一管理員固定最大權限 | 系統只剩 1 位啟用 admin 時，其全部權限強制開啟（防互覆蓋後鎖死） |
| 保護底線 | 任何操作後系統必須仍有 ≥1 位啟用中且持有 `user-mgmt` 的帳號，否則拒絕該操作 |

### 2.2 稽核紀錄

所有帳號操作（新增／改權限／改角色／啟停／刪除／重設密碼）寫入 `user_audit_log`（誰在何時動了誰），管理員可查（`GET /api/users/audit`）。帳號刪除後稽核軌跡保留（target 欄位清空但不滅證）。

## 三、網頁操作：管理使用者與權限（僅 admin）

### 3.1 入口
登入後 → 右上角「**👥 帳號與權限**」→ 進入「帳號與權限」頁面（`/permissions.html`）。

- **桌面**：左側帳號列表 + 右側操作面板
- **手機**：頂部 chip 橫滑列選帳號 + 下方操作面板

### 3.2 新增帳號
1. 右上角「**＋ 新增帳號**」
2. **單一新增**：帳號、顯示名稱、角色、密碼（8 碼以上，含大小寫與數字）——前端送出時即時檢查密碼政策（`pwPolicyMsg()`），不合规會 toast 提示
3. **批次新增**：每行一筆 `帳號, 顯示名稱, 角色, 密碼` → 逐列回報結果（成功綠／失敗紅，成功的保留、失敗的不回滾）
4. 帳號**不可重複**

### 3.3 權限設定（🔐 權限設定 tab）
1. 左側（或手機 chip）選一位帳號
2. 35 個權限開關分 4 組（📋 瀏覽與匯出／📦 庫存管理／📅 行事曆與派工／⚙️ 系統設定）
3. 開關旁標記來源：**🔒 鎖定**（系統強制，不可改）、**✏️ 自訂**（個人覆蓋）、**✓ 跟隨角色**（角色預設）
4. 調整後按「**💾 儲存變更**」→ 立即生效、不需重新登入
5. 「**↩ 重設為角色預設**」= 清除該帳號全部個人覆蓋
6. **自己的權限無法修改**（系統保護）；權限頁對自己顯示鎖定狀態

### 3.4 頁面顯示設定（🖥 頁面顯示）

權限頁的「頁面顯示」區塊讓管理員針對每一個帳號逐頁控制入口是否顯示，頁面清單包含：行事曆、每日簽名日報表、報價單、零用金月報、單一庫存、待領出、已領出、盤點、整組庫存、帳號與權限、系統設定、修改密碼。

- 每個頁面獨立開關，不綁定角色；角色只在新建／既有資料首次初始化時提供預設值。
- 管理員預設全部開啟。
- viewer 預設開啟行事曆、每日簽名日報表、單一庫存、整組庫存，其餘關閉。
- user／tech 為相容既有入口，初始化時全部開啟；之後只依個人設定保存，不會因角色變更覆蓋。
- sidebar 與右上角選單共用同一組設定；前端只負責隱藏入口，後端 page-visibility API 仍要求 `page-visibility-manage`。
- 實際可用入口契約為 **Page Visibility ∩ RBAC Capability**：sidebar、`?tab=` deep-link、fallback、月底盤點提醒、standalone settings／permissions guard 都必須使用同一判定；頁面隱藏不取代後端 `require_perm(...)`。

### 3.5 帳號設定（🔑 帳號設定 tab）

選取其他帳號後，可按「**✏️ 編輯帳號**」用同一個編輯視窗修改：

- **顯示名稱**：最長 100 字；儲存後左側帳號列表、手機 chip 與標題會同步更新
- **角色**：從 admin / user / tech / viewer 選擇；後端會再次驗證角色白名單
- 儲存使用既有 `PUT /api/users/{id}`，變更立即生效，不需重新登入
- 不能編輯自己的角色；後端仍會保護最後一名啟用管理員
- 角色變更寫入 `user_audit_log` 的 `role_change` 紀錄
- 日後若增加可編輯欄位，應擴充同一個編輯視窗與更新 payload，避免每個欄位各自維護一套 modal／API

| 操作 | 按鈕 | 說明 |
|---|---|---|
| 編輯帳號 | ✏️ 編輯帳號 | 修改其他帳號的顯示名稱與角色；不可修改自己的角色 |
| 重設密碼 | 🔑 重設密碼 | 不需知道舊密碼 |
| 停用／啟用 | ⏸ 停用帳號 / ▶️ 啟用帳號 | 停用後立即無法登入（含既有 session）；**離職員工請用停用而非刪除** |
| 刪除帳號 | 🗑 刪除帳號 | 不能刪自己；有派工紀錄的帳號無法刪除（改用停用）；系統保護底線：最後一位管理員不可停用／刪除／降級 |

### 3.6 使用者綁定 Google 行事曆 Key（📅 行事曆同步）

每位使用者可綁定一把 Google 同步 Key（`users.gcal_key` 欄位），決定該使用者被指派的行程同步到哪本行事曆。

**設定方式**（admin）：
1. 先在「⚙️ 設定 → 📅 行事曆同步」建立至少一把 Key
2. 在同一頁面下方「使用者綁定 Key」區塊，為每位使用者選擇綁定的 Key
3. 或透過 API：`PUT /api/users/{id}` body `{ "gcal_key": "廠商A" }`

**同步邏輯**：
- 行事曆行程新增/編輯/刪除時，系統查指派人員的 `gcal_key` → 找對應的 `gcal_keys` → 寫入 sync_queue
- 指派人沒綁 Key → **fallback 到所有啟用 Key**（全部同步）
- 同一行程指派多人（不同 Key）→ 同步到多本行事曆

**權限**：綁定 Key 需 `user-mgmt` 權限（admin only）。

> 完整 Google 同步說明見 `docs/行事曆維護文件.md` §3。

## 四、權限怎麼被執行的（白話版）

| 層級 | 機制 | 效果 |
|---|---|---|
| **後端（真正的防護）** | 每個 API 端點掛 `require_perm(key)`：無該權限 → `403 無此權限` | **38 個寫入端點 + 可關閉瀏覽端點全量權限控管**，即使有人直接打 API 也會被擋 |
| **前端（UX 防呆）** | `hasPerm(key)` 依 `/api/auth/me` 回傳的 permissions 判斷按鈕顯示 | 沒權限的人「看不到」不能做的操作；關閉某權限後，對應按鈕立即隱藏 |
| **權限合成** | 每次請求即時重算：角色預設 + 個人覆蓋 + 強制規則 | 改權限後下一請求立即生效、不需重新登入 |

**重點**：前端隱藏只是讓畫面乾淨，**後端 403 才是安全邊界**。

## 五、使用者密碼與安全規則

- 密碼以 **PBKDF2-HMAC-SHA256（600,000 次迭代）** 儲存，資料庫不存明文
- 連續 **5 次登入失敗 → 鎖定 15 分鐘**
- 密碼最少 **8 碼**且須含大小寫與數字
- **自行改密碼是權限開關（`change-own-password`）**：current seed 對 Admin、User、Tech、Viewer 均預設開啟；Page Visibility 可控制入口顯示。被關閉 capability 的帳號由管理員重設，且**不顯示密碼過期提示畫面**（R2）
- 密碼過期（180 天）：有自行改密碼權限者顯示「立即改密碼／繼續使用原密碼」；無權限者顯示「請聯絡管理員重設」

## 六、開發者：權限異動維護 SOP

> 當要「新增一個權限」或「調整某角色的預設值」時，依下列清單逐項修改，**避免改了程式碼卻漏同步文件**。

### 6.1 單一真源（Single Source of Truth）

| 真源 | 用途 | 檔案 |
|---|---|---|
| **資料庫 seed（唯一真源）** | 角色／權限點／角色預設矩陣 | `app/database.py` 的 RBAC 區塊（roles/permissions/role_permissions seed） |
| 合成邏輯 | 角色預設 + 個人覆蓋 + 強制規則 | `app/services/auth.py` 的 `get_user_permissions()` |
| 權限守衛 | 端點掛載 key | 各 `app/routes/*.py` 的 `require_perm("key")` |
| 角色白名單 | 建立帳號允許的角色 | `app/routes/users.py` 的 `ALLOWED_ROLES` |
| 權限目錄 | 權限說明（本文件 §一/§二/§2.1） | **本文件**（唯一真源） |

### 6.2 調整流程（例：開放工程師的盤點權限）
1. `app/database.py` seed 矩陣：`tech` 的 `stocktake` 改 1 → 重啟 server（SQLite seed 冪等，既有 DB 重跑 init_db 即生效）
2. 權限頁自動顯示新狀態（權限點清單由 per-user 端點 `/api/users/{user_id}/permissions` 內聯載入，**前端無需改**）
3. 同步更新本文件 §二（權限矩陣為唯一真源）
4. 跑 `tests/test_rbac.py` / `tests/test_rbac_perms.py`（矩陣比對會驗證 seed）

### 6.3 新增權限點
1. `permissions` 表加一筆（key/label/module）
2. seed 矩陣各角色給預設值
3. 端點掛 `require_perm(新key)`
4. 權限頁自動出現新開關（無需改前端）
5. 測試：test_rbac_perms.py 的 EXPECTED_MATRIX 同步 + 端點矩陣

### 6.4 Google 行事曆同步相關異動

| 異動類型 | 需改的位置 |

| 新增使用者綁 key | `app/database.py` migration（users.gcal_key）+ `app/routes/users.py` PUT |
| 調整同步邏輯 | `app/services/gcal_sync.py` |
